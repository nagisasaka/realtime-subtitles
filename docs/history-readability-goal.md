# 履歴再翻訳・再分割の短時間最適化

## 起動用の短いゴール命令

```text
/goal docs/history-readability-goal.mdに従い、履歴再翻訳の読みやすさを固定データで反復評価・改善する。各回5分目安・最大10分。翻訳忠実性と英日対応を維持し、採否の根拠・再現手順・最終判断を残す。
```

この文書の作成だけでは評価を開始しない。ユーザーがこのゴールを開始した時点で、以下の範囲で実装・実API評価・プロンプト変更・テスト・commitを行う。
目的は無期限の最適化ではなく、限られた実験で採用可能な改善を見つけ、見つからない場合も根拠付きで現状維持を決定すること。

## 保持するもの・変更できるもの

- 開始時にGit状態・worktree・ローカル指示を確認し、開始commitと現行プロンプトを保存する。未commit変更を破棄しない。
- 他スレッドと競合する場合は `experiment/history-readability` 等の専用branch/worktreeを使う。この仕様書も持ち込む。競合しなければmainで作業してよい。
- `openai-stable-v1` と `experiment/speechmatics` は変更しない。他スレッドのworktree・評価結果には書き込まない。
- Linden 1、ライブ認識、最初の翻訳、マイク・音声送信、GUI、保存形式、話者境界は維持する。
- 主な変更対象は `src/realtime_subtitles/history_reconstruction.py` の再構成プロンプト、専用評価スクリプト、テスト、説明文書。
- `gpt-6-luna` / `reasoning.effort=none` を維持する。ASR本文の訂正、英文生成による置換、文字数だけでの強制結合は禁止。
- 最初はウィンドウ・context・schema・モデルを固定し、プロンプトだけを変更する。入力ウィンドウ端が主要因なら、それを報告し、この実験ではウィンドウ設計を変更しない。
- 稼働中アプリの停止・自動再起動・配布先への上書き、pushは行わない。

## 現状と原因の分類

作成時点では、同一話者/sessionの隣接TranslationUnitを2個、次に最大3個へ拡張し、最大1,800文字を再翻訳する。実際の開始時のコードを再確認する。
現在は英文境界だけを先に決め、固定したチャンクIDごとの翻訳を次の1回で一括生成する2段階方式。
英文は原文tokenの範囲指定で保持する。構造検証は英文tokenの完全被覆、翻訳IDの過不足・重複と非空訳を検査し、意味のまとまりの保証ではない。
旧方式の `run1` / 既存manifest・結果は歴史的記録として保持し、書き換えない。新方式の評価には方式と2つのプロンプトを記録した新manifestを作る。

短い段落の原因を次に分類する：

1. 完了したLLM再構成の内部境界。
2. 対象ウィンドウの端、話者/sessionの境界。
3. 未完了・失敗・queue overflow等による元TranslationUnitへのフォールバック。
4. Widgetの折り返し。意味的な段落境界とは別。

プロンプト評価の対象は主に1。2〜4を混ぜて「LLMが細かく分割した」と数えない。

## データを固定する

- 優先入力は既存Earnings22のraw `AddSegment`。音声再送・新規ASR・全編再生は不要。
- 現在の取得候補：`/workspace/jimaku-earnings-benchmark/benchmark_results/earnings22/20261008_arqit_completed/transcript.jsonl`、同階層の `events.jsonl` と `manifest.json`。
- Qudian `4474955`、Arqit `4475604` を利用する。存在・正常EOS・データの対応を確認し、必要部分だけ自分の結果directoryへsnapshotする。元を変更しない。
- 句読点を含むraw英文、segment ID、時刻、speaker、session、受信順を保持する。WER用正規化済み英文を翻訳に使わない。
- 連続した説明、数字/固有名詞、短い応答・話者交代を含む合計3〜5分程度から、原則12個の評価ウィンドウを選ぶ。失敗しそうな例だけを選ばない。
- 本番のTranslationUnit構築と再構成window plannerを可能な限り再利用する。途中から抽出する場合も前方の文脈とグルーピング状態を復元し、不自然な切断を作らない。
- 調整用8件、最終確認用4件へ事前に分割。同じ英文を含む2単位版・3単位版や隣接contextが両群に跨らないよう、録音内の離れた区間単位で分ける。
- ID、元ファイルhash、抽出位置、raw本文、context、window構成、開始commit、選定理由、分割をmanifestに保存して以後固定する。
- 最終確認用の出力・採点は採用候補が決まるまで開かない。結果を見て調整に戻るなら、それは確認用ではなくなったと明記する。
- 人手英文GTはASR誤りの診断用。日本語訳や段落の正解とみなさない。GTでASR入力を差し替えない。
- Earnings22が使えなければ既存の講演rawログを探す。代替データと限界を明記し、新たなASR評価は始めない。

## 1イテレーションの運用

1. 仮説を1つ書く。例：ASRの句点に引きずられ、説明の導入と本体を分けすぎる。
2. 指示・few-shot例など、変更点を1つに絞る。例は調整用だけから作る。
3. 固定した調整用8件で候補を生成する。現行baselineの同じ入力結果はcacheから利用する。
4. 自動検査と匿名A/B採点を行い、改善・悪化例を確認する。
5. 所要時間、全件数、失敗件数、指標、採用/棄却/保留、次の仮説を保存して短く報告する。

開始から記録終了まで5分を目安、最大10分。初期の評価器作成も10分以内の保存可能な小作業に分けるが、実装進捗を品質改善として数えない。
評価runnerはmonotonic時計のdeadlineを持ち、実API待機を含め480秒で新規処理を止め、残り120秒をキャンセル・保存・報告用に確保する。
APIごとに最大45秒かつ残りdeadline以下のtimeout、同時実行最大2。SDKの暗黙retryを止め、翻訳の明確な検証失敗に対する最大1回retryだけを明示的に数える。
時間切れは未完了として保存し、成功例だけで採用判定しない。次回は同じ候補の未処理分から再開できるようにする。
5分は目安であり、品質検査を省いて帳尻を合わせない。runnerに加え編集・レビュー時間も記録する。

## 評価方法

### 機械的な必須検査

- 英文を一切変更せず、token範囲が単調・完全被覆・重複なし。
- 日本語の各部分が非空で、固定した英文チャンクIDに過不足・重複なく対応する。
- 話者境界を跨がない。既存TranslationValidatorの数値・通貨・単位等の検査を維持する。
- 応答時間、retry、schema/validation失敗を全件記録。未完了を欠測として表示する。

### 読みやすさの指標

| 指標 | 用途 |
| --- | --- |
| 英文100語あたりの不適切な内部境界数、絶対件数 | 主指標。ひと続きの説明・修飾関係・列挙導入を不要に切った箇所 |
| 各英日ペアの意味対応不良件数 | 別段落の内容が訳に混入、対応部分の欠落など |
| チャンク訳の重大誤り件数 | 数字・否定・主語・固有名詞・事実の変化、欠落、過剰補完 |
| 過度な結合件数 | 異なる話題を一塊にして追いにくくした箇所 |
| 5語以下の英文段落率、語数中央値、100語あたり段落数 | 診断値のみ。短いほど悪いとは採点しない |
| 固定した表示幅・EN/JAフォントでの段落別visual lines | 視覚的な占有量。条件と実測/推定を明記 |
| API latency p50/p95、retry率、構造検証失敗率 | 少数標本の記述値。厳密な性能保証とはしない |

`Yes.`、`Thank you.`等の独立した短い発話は正常。最低語数や段落数だけを目的関数にしない。
境界は「適切／不要な分割／判断困難」に分類し、隣接する原文と理由を保存する。ウィンドウ端は別集計。
正しい分割が複数あり得るため、唯一の正解境界との完全一致を要求しない。

### 意味の判定とA/B比較

- 本番と独立した採点プロンプトを固定し、元英文・必要な前文脈・候補2つを匿名で提示する。
- 各観点についてA勝ち/B勝ち/同等/判断困難と、問題となる原文・訳文の範囲・短い理由を構造化して保存する。
- 表示順をseed固定で入れ替える。重要な2例は順序を逆にして採点が変わらないか確認する。
- 自動judgeは当初 `gpt-6-luna` を別request・固定指示で使用し、使用モデルを保存する。同モデルの自己評価に由来する偏りを明記する。モデル追加・変更による探索はしない。
- 代表例と全悪化例をCodexでも読み直す。これは独立した人間評価ではない。ユーザーが後から確認できる匿名比較表を用意し、人間未確認ならその旨を明記する。
- 採点基準を候補が有利になるよう変更しない。採点器を修正する必要があれば全候補を同じ基準で再採点する。
- 判定の一致を客観的真実や統計的有意差と表現しない。

まず本番と同じ英文分割→一括翻訳の2段階で比較する。分割プロンプトを比較するときは翻訳プロンプトを固定する。翻訳だけを調べる補助実験では英文境界を固定し、本番全体のスコアへ混ぜない。

## 採用基準と停止条件

プロンプト候補は最大3案。2案連続で改善がなければ探索を終える。採点を都合よく変更して継続しない。
APIは生成・採点・retry・失敗を含め全体80 request attemptsまで。送信前に永続ledgerへ予約し、再起動してもリセットしない。出力上限も明示し、usageと実測latencyを保存する。現在の価格を確認できない場合は金額を捏造しない。

候補の採用には次を満たすこと：

1. 調整用の構造検査が全件成功し、チャンク訳の重大誤り・英日対応不良がbaselineより増えない。新たな重大誤りがある候補は採らない。
2. 不適切な内部境界の絶対件数が減り、A/Bで読みやすさの勝ちが負けを上回る。短段落率の低下だけでは採らない。
3. 過度な結合が増えず、応答時間の中央値がbaselineの1.25倍またはbaseline+1秒の大きい方を超えない。同一条件で測り、外れ値は削除せず説明する。
4. 選んだ1候補を確認用4件でbaselineと比較し、重大な新規誤り・対応不良・不要な分割の悪化がない。
5. 改善根拠となる調整用2件をbaseline/候補とも再生成し、改善方向が反転しない。不安定なら保留する。

baseline自体に不適切な境界がない、差が小さい、確認用で悪化、予算/時間制約で根拠不足の場合は現行プロンプトを維持する。
「改善の採用」または「上限内の評価を終え、根拠付きで現状維持を決定し、成果物を完成」がこのゴールの正常な完了。後者を品質改善達成とは報告しない。
認証・データ不足で評価できない場合は、実行可能部分と具体的な不足を記録し、品質評価済みとはしない。goal状態の変更はツール側の規則に従う。

## 成果物・検証・Git

- 評価実装：`benchmarks/history_readability/`。既存コードを利用し、大規模な評価基盤は作らない。
- 生成物：`benchmark_results/history_readability/<run>/` にmanifest、固定入力、全応答、指標、採点、iteration log、API ledger、最終 `report.md`、匿名比較表を保存する。機密・元データ・生成ログをcommitしない。
- 再開時は前回のmanifest/ledger/iteration logを読む。baseline・候補・入力・context・judge promptのhashをcache keyに含める。指定した再生成はcacheを使用しない。
- script・README・合成の小さなfixture・テストはGit管理。取得元とライセンスを記録する。
- APIなしのテストで、原文保持、window/context固定、段落被覆、英日連結一致、cache識別、deadline、失敗保存、採点集計、予算上限を確認する。
- 候補採用時は既存再構成/翻訳/表示関連テストとlintを実行する。コード変更に応じた既存全体テストは最終段階で行い、毎試行繰り返さない。
- 最後に可能ならWindows nativeで保存結果を60〜90秒のイベント順に再生し、同じ幅・DPI・フォントで比較する。新たなSpeechmatics送信は不要。表示再生は実音声end-to-end検証とは区別する。
- 稼働アプリに触れず別のプレビューを使う。Windowsが使えなければ表示は未検証として報告する。
- 採用が妥当なら最小限のプロンプト変更をcommit。採用なしでも再現可能な評価器と説明をcommitする。開始時の他人の変更を混ぜない。branch、commit、working tree状態を報告する。
- 最終報告は、試行ごとの時間、改善前後の実数、英日実例、翻訳品質への影響、失敗/スキップ、使用request数、確認用結果、採否、残課題を簡潔に示す。
