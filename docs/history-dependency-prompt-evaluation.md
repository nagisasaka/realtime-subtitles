# 履歴の英文分割プロンプト改善とEarnings22評価

2026-10-08、変更前 `c4fe588`。**英文分割のプロンプトだけを変更して採用した。**
主語と述語、動詞と目的語、修飾句の分断は減った。ただし、すべての細切れや翻訳の意味誤りが解消したわけではない。

## 変更

`history_reconstruction.py` の `SPLIT_INSTRUCTIONS` で、ASRの句読点・大文字始まり・streamingの切れ目を文境界と決めつけず、
文法上のつながりを先に確認するよう指示した。動詞の後に遅れて出る目的語、列挙の続き、関係節、修飾句を保持する。
独立した話題・短い完結した返答は分け、window外の続きを生成しない。
例示には合成した英文を使い、評価データの原文や日本語正解をプロンプトへ埋め込んでいない。

英文をモデルに書き直させず、token indexから原文を切り出す方式、最大3 TranslationUnits・1,800文字、
チャンクID付き一括翻訳、翻訳プロンプト、モデル、Validator、queue、ライブ表示は変更していない。
通常のAPI呼び出し数も履歴1範囲につき2回のまま。追加の文法判定APIやルールベースの結合処理はない。

## 評価条件

Earnings22のQudian `4474955` / Arqit `4475604` から取得済みLinden 1出力を使用。
ASRへ再送せず、同じ英文・CONTEXT・翻訳プロンプトで比較し、分割変更の効果を調べた。
比較相手は直前の英文先行分割版で、旧「全文日本語生成」方式ではない。

- 既知の比較8窓で最大3候補を試し、candidate3を選定。
- 以前すでに開いた追加4窓で確認。ファイル名は `holdout.json` だが、未見holdoutとは呼ばない。
- 選定後、この調整で未使用の2窓を追加。元12窓と原文・CONTEXTのsource IDが重複しないことを検証。
  出力を見る前にmetadataだけから `4474955-r25` / `4475604-r12` を固定した。
- 合計14窓、**275.40秒相当**。追加2窓は30.48秒。この小標本は会議全体の品質を代表しない。
- モデルは両段階 `gpt-6-luna / reasoning.effort=none`。生成と固定judgeは別requestだが、同一モデルのため独立した人間評価ではない。

## 結果

| 対象 | 改善前の段落数 | 改善後の段落数 | 5語以下（前→後） | 構造・ローカル検証（後） |
|---|---:|---:|---:|---:|
| 調整用8窓 | 30 | 23 | 4→2 | 8/8 |
| 既知の追加4窓 | 19 | 17 | 2→2 | 4/4 |
| 調整後に追加した2窓 | 6 | 5 | 3→1 | 2/2 |
| 合計 | **55** | **45** | **9→5** | **14/14** |

全文tokenの欠落・重複なし。全14窓で再翻訳0回。短いだけでは誤りと判定せず、元のASR本文を保持した。
既知12窓で照合した文法依存11箇所のうち、9箇所で元の境界がなくなり、2箇所は残った。
これはCodexによる対象箇所のレビューで、網羅的な人手正解率ではない。

具体例：

- Qudian 28.04–58.04秒：役職を含む話者紹介と `will start the call` が同じ段落になった。
  「チュー氏が、」だけが独立する表示を回避。
- Qudian 147.80–163.32秒：`execute. / Prudent... / At a stable level.` が3段落から1段落に。
  訳は「第3四半期は市場環境が急速に変化する中、慎重なオペレーション戦略を引き続き実行し、
  キャッシュクレジット事業の資産の質を安定した水準に維持しました。」となった。
- Arqit 81.12–104.88秒：`The company is providing.` と `That information...` の分断を解消。
- Arqit 263.36–281.80秒：製品投入と `Onto the global market...` は結合されたが、
  `By virtue of that Nasdaq listing.` と後続主節はまだ別段落。
- 未使用2窓では、都市名と「すべて高品質…」の対応が1段落になり、別の独立した3文は3段落のままだった。

問題例2件（Qudian r5/r13）はcacheを使わず再生成し、改善後の英文境界が同じだった。
日本語表現は変化したが、主語・述語等のつながりは維持された。

## 自動採点と残課題

固定の匿名judgeでは、既知12窓の読みやすさが8勝1敗3引き分け、追加2窓は1勝1引き分け。
ただし主指標にはしない。問題例2件でA/B提示順を反転すると、r5は改善後優位を維持した一方、
r13は「短い段落の方が拾い読みしやすい」と改善前優位に反転した。採点理由でも新しい結合は同じ話題と認めている。
judgeには通貨単位の重複を重大な金額誤りとする判定や、1つの孤立句を両側で二重計上する判定もあった。

残課題：

- window端の `With our.` など、続きを含まない断片は残る。現在のwindow上限は変えていない。
- 列挙の導入と項目、前置き句と主節の結合がまだ安定しない。
- つながりを保つ分、1段落は長くなる。短さだけを最適化すると分断が戻るため、読みやすさには実使用での確認が必要。
- `public shareholders`→「個人株主」、`And citizens.`→「市民のデータ」、
  `High quality`への「サービス」の補完がローカルValidatorを通る。
  誤りや補完は改善前にもあり、今回の分割プロンプトで翻訳全般の忠実性が解決したとはしない。
- 境界が変わらない窓での日本語の差は生成の揺れを含み、分割プロンプトの効果と数えない。

## 所要時間・Windows・テスト

採用候補の既知12窓はAPI待ち合計のp50 **3.15秒**、p95 **4.16秒**。
調整中に同一入力の翻訳・judge結果をcacheから再利用したため、各出力に保存された実API待ちの合計であり、
全件を同時刻に再測定した値ではない。変更前のp50 3.62秒 / p95 5.20秒も以前の保存値で、速度向上の根拠にはしない。
新規2窓で両案をcacheなしで測ったAPI待ちは中央値3.25→2.66秒だが、2件だけなので速度差を一般化しない。
音声認識・queue待ち・UI反映・window成立待ちは含まず、ライブ字幕の遅延ではない。

生成と採点を含む各dev実行は29.10秒 / 16.63秒 / 10.30秒、追加4窓15.81秒。
後の候補ほどcacheを使うため、これも案間の速度比較ではない。準備・レビュー時間は別。
合計76 API attempts（上限80）、入力99,860 / 出力10,904 tokens。金額は未算出。

- WSL関連テスト：**96 passed**。Ruff lint/format・diff check成功。
- Windows native関連テスト：**70 passed**（履歴処理・評価・UI）。
- Windows native Tkで既知8窓を64.54秒表示、168 DPI、各列1,268×1,092px、callback error 0。
  同条件のvisual linesはEN43→42、JA30→27。最大英文段落は3→4行となった。
  保存結果の表示診断であり、録音のリアルタイム再生や人間の読みやすさ評価ではない。
- 稼働中アプリやマイクは再起動していない。Windows起動用ソースへ反映し、次のアプリ起動から適用する。
